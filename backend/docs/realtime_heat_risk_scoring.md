# 실시간 폭염위험 점수체계 및 작업 방향

## 1. 목적

이 문서는 방안 C에 따른 실시간 폭염위험 계산의 기준, 코드 구조, 한계와
향후 작업 순서를 한곳에서 관리한다. 점수는 피해 발생 확률이나 의학적 진단이
아니며, 현재 기상위험과 지역 취약성을 설명하고 행정동 대응 순서를 돕는
탐색형 지표다.

## 2. 방안 C의 원칙

하나의 점수에 모든 자료를 섞지 않고 다음 값을 분리한다.

1. `H` 실시간 기상위험: 지금 날씨가 얼마나 위험한가
2. `V` 지역 취약성: 같은 날씨에서 해당 지역이 얼마나 불리한가
3. `P = H × V` 대응 우선순위: 같은 시점의 행정동 정렬·지도 색상용 보조값

사용자 화면에는 H와 V를 각각 보여주고 원인별 세부값을 제공한다. P는 피해
확률로 표현하지 않는다.

## 3. 입력 데이터

### 실시간 기상

- 기상청 초단기실황 `T1H` 기온과 `REH` 습도로 계산한 체감온도
- 기상청 초단기실황 `WSD` 풍속
- 발표시각과 이전 저장값 사용 여부

체감온도에는 기온과 습도가 이미 포함되므로 기온·습도를 다시 독립 점수로
더하지 않는다.

### 열환경

- `heat_indicators.csv`의 불투수면 위험
- `heat_indicators.csv`의 녹지 부족
- `building_density_by_dong.csv`의 행정동 건물 바닥면적 비율

세 지표는 도시화 정도와 상관성이 높으므로 각각 최종 가중치로 사용하지 않고
하나의 열환경 영역 E로 묶는다.

### 쉼터 접근성

- 행정동별 운영 중인 무더위쉼터 수와 운영 요일·시간
- 원자료에서 `누구나이용가능`으로 판정된 쉼터 수
- 2026년 7월 행정동별 총인구

시설명만 보고 경로당 등을 임의로 제외하지 않는다. 원자료의 이용 가능 판정을
사용해야 분류 기준을 추적하고 갱신할 수 있다.

전처리 시 논공읍공단출장소는 논공읍, 다사읍서재출장소는 다사읍 인구에
합산한다. 위치코드·주소상 군위군 산성면에 해당하는 `산정면` 표기 및 행정동
불일치 자료 28건을 산성면으로 보정한 뒤 모든
자료를 기존 지도와 동일한 150개 `adm_cd`로 결합한다.

## 4. 현재 계산식

### 4.1 실시간 기상위험 H

체감온도는 고정 기준점 사이를 선형 보간한다.

| 체감온도 | 위험값 |
|---:|---:|
| 26℃ 이하 | 0.00 |
| 29℃ | 0.20 |
| 31℃ | 0.40 |
| 33℃ | 0.60 |
| 35℃ | 0.80 |
| 37℃ 이상 | 1.00 |

이 기준은 프로젝트 1차 운영값이며 공식 피해확률 기준이 아니다. 행정동별 피해
자료가 확보되면 검증 후 `weather_risk.py`의 기준점만 교체한다.

저풍속 위험 W는 0m/s에서 1, 4m/s 이상에서 0이 되도록 선형 변환한다.

```text
H = T + (1 - T) × W × 0.20
```

T는 체감온도 위험이다. 풍속은 실제 골목 풍속과 다를 수 있어 H를 낮추지 않고
남은 위험범위의 최대 20%만 높인다. API에 풍속이 없으면 `H = T`다.

### 4.2 열환경 E

```text
I = 기존 150개 행정동 불투수면 정규화값
G = 기존 150개 행정동 녹지부족 정규화값
B = 건물밀도의 150개 행정동 최소-최대 정규화값
E = (I + G + B) / 3
```

건물밀도 정규화 범위는 전체 자료의 0.1742%~52.2223%다. 데이터가 갱신되면
저장소가 실제 최솟값·최댓값을 다시 읽는다.

### 4.3 쉼터 대응 취약성 A

```text
현재 이용 가능한 일반인 쉼터 = 운영 중 + 누구나 이용 가능 + 현재 요일·시간 일치
A1 = 1 - (현재 이용 가능한 일반인 쉼터 / 운영 중인 쉼터)
현재 공급량 = 현재 이용 가능한 일반인 쉼터 / 인구 × 10,000
A2 = 1 - 고정 범위 최소-최대 정규화(현재 공급량)
A = (A1 + A2) / 2
```

운영 쉼터가 0곳이면 A1은 1이다. A2의 정규화 범위는 전처리 시점의 150개
행정동별 `운영 중이며 누구나 이용 가능한 쉼터/인구 1만 명` 분포로 고정한다.
따라서 요청 시점마다 순위에 맞춰 점수가 재조정되지 않는다. 현재는 요청대로
A1과 A2만 동일 비중으로 결합하며 수용인원·면적·거리는 포함하지 않는다.

### 4.4 지역 취약성 V와 대응 우선순위 P

```text
V = (E + A) / 2
P = H × V
```

각 세부 항목을 한 번에 평균하지 않고 열환경과 쉼터라는 두 영역을 먼저 묶어,
자료 열이 많은 영역이 자동으로 더 큰 비중을 얻지 않게 한다. 동일 평균 역시
모형 선택이므로 향후 결과자료로 반드시 검증한다.

## 5. 등급

H, V, P 각각을 설명 편의를 위해 고정 구간으로 표시한다.

| 0~1 점수 | 등급 |
|---:|---|
| 0.00 이상 0.25 미만 | low |
| 0.25 이상 0.50 미만 | moderate |
| 0.50 이상 0.75 미만 | high |
| 0.75 이상 | critical |

현재 시점의 최솟값·최댓값으로 등급을 바꾸지 않으므로 서로 다른 시간의 등급을
비교할 수 있다.

## 6. 코드 구조

```text
backend/heat_risk/
├─ normalization.py       공통 0~1 변환과 선형 보간
├─ weather_risk.py        체감온도·풍속 기반 H
├─ thermal_environment.py 토지피복·건물밀도 기반 E
├─ shelter_access.py      일반인 쉼터 기반 A
├─ repository.py          CSV 읽기와 행정동 결합
└─ scoring.py             H, V, P 조합과 등급

backend/scripts/
└─ preprocess_shelter_access.py  출장소 합산·산성면 보정·행정동 코드 결합
```

FastAPI 연결 주소:

```text
GET /api/realtime-heat-risk
GET /api/realtime-heat-risk/{region_code}
```

첫 번째 주소는 지도 전체 150개 행정동, 구·군 평균과 순위를 반환한다. 중복 없는
기상청 격자의 SQLite 실황을 재사용하므로 지도 요청 시 API를 150번 호출하지
않는다. 두 번째 주소는 선택 행정동 상세값을 반환한다.

기존 `/api/heat-vulnerability`와 그 산출 파일(`heat_vulnerability.json` 등)은
지도 화면에서 쓰이지 않아 삭제했다. 지도는 P, 상세 패널은 H·V·P를 표시한다.
기상 실황이 없는 동은 기존 점수로 대체하지 않고 데이터 없음 색상으로
표시한다.

## 7. API 응답 핵심 구조

```json
{
  "status": "ready",
  "scores": {
    "weather_hazard": {"score": 0.0, "level": "low"},
    "regional_vulnerability": {
      "score": 0.0,
      "level": "low",
      "thermal_environment": {},
      "shelter_access": {}
    },
    "response_priority": {"score": 0.0, "level": "low"}
  }
}
```

기상청 자료가 없으면 임의의 날씨값으로 계산하지 않고 `scores: null`과
`unconfigured` 또는 `unavailable` 상태를 반환한다.

## 8. 한계

- 5km 기상 격자값은 행정동 내부의 미세기후와 다를 수 있다.
- 건물밀도는 높이·층수·바람길을 포함하지 않는 수평 건물 피복률이다.
- 불투수면, 녹지부족, 건물밀도는 상관성이 높다.
- 풍속 보정 상한 20%는 검증 전의 명시적 운영 가정이다.
- 쉼터 운영표는 공개된 요일·시간을 사용하므로 임시 휴관은 즉시 반영되지 않는다.
- A2는 행정동 총인구 기준이며 실제 주간 체류인구와 쉼터 수용인원은 미반영이다.
- H×V는 절대 위험이나 환자 발생 확률이 아니다.

## 9. 다음 작업 순서

1. 새 API 결과를 기존 팝업에 H와 V 두 줄로 표시한다.

3. 쉼터 임시 휴관·혼잡도 또는 잔여 수용인원을 확보한다.

6. 행정동별 온열질환·구급출동·지표면온도 자료로 기준과 결합식을 검증한다.
7. 검증 전후 점수 분포와 순위 안정성을 비교한 뒤 운영 버전을 확정한다.
